**F01 / P1 / Android 取消被阻塞请求饿死。** `WailsJSBridge.java:136–149` 将所有调用（含取消）送入同一个执行器；核心线程 2、队列 64，队列未满时不会扩到最大 4 线程。Wails beta.30 的 `processCallMethod` 同步执行绑定，`CancelCall` 需要另一条 runtime 调用才能取消它。两个阻塞绑定占住核心线程后，取消请求排入队列，只有原请求自行结束才可被处理。对真实 Java 桥的受控实验得到 `cancelReachedNative=false, poolSize=2, queueSize=1`，释放阻塞后取消才到达。证据：`dist/audit/full-project/java-probe/result.log`；复现脚本 `.cache/audit-bridge.mjs`。期望取消有独立可达的控制路径，并处理排队中尚未进入 Go 的请求；不是简单扩大线程池。尚未实机测弱网和切页。

**F02 / P2 / 服务启动失败未回收部分资源。** `app/service/app.go:311–373` 在打开数据库之后，策略读取、解码、初始化均可提前返回，未关闭数据库或取消 `NewApp` 的独立后台所有者。隔离库注入无效 `network_request_policy_v1` 设置后，启动返回 STORAGE 错误，但数据库仍可 Ping，background context 未取消。已核对 beta.30 `application.go:681–687`：仅成功启动的服务被加入 shutdown 清单，因此不能依赖框架清理失败服务。证据：`startup-probes.log` 中 `TestAuditStartupPolicyFailureReleasesResources`。期望失败路径回滚已拥有资源；没有宣称已复现用户数据损坏。

**F03 / P2 / 数据库打开错误升级为 panic。** `app/service/app.go:351–352` 没有返回 `ServiceStartup` 的 error，而是 panic。用临时目录中的同名数据库目录触发 SQLite 打开失败，确实得到 panic；权限／存储故障也走这个分支。证据：`TestAuditStartupDatabaseFailureDoesNotPanic`。此测试只证明启动边界行为，桌面错误展示与 Android 崩溃表现待原生验证。需要与顶层 `main.go` 错误呈现一并处理，不能只改一行便声称恢复体验完成。

**F04 / P2 / 窗口设置写失败仍返回成功。** `app/window/service.go:51–57,119–148` 先应用内存／窗口状态，再忽略数据库写错误；相应 façade 无 error 返回。临时库使用拒绝 settings INSERT 的触发器后，`SetCloseBehavior(false)` 正常返回，但内存为 false、数据库仍为 true，重启恢复旧值。`SettingsBasicGroup.vue` 的 catch 收不到错误；尺寸的宽高两次独立写入还存在部分成功的路径。已复现关闭行为，尺寸部分写入待追加验证。证据：`TestAuditWindowSettingRejectsFailedPersistence`。

**F05 / P2 / “关闭到托盘”设置没有接入窗口关闭路径（代码确认）。** 生产代码中 `shouldMinimizeToTray` 没有调用方；`TitleBar.vue:56–58` 直接 `Window.Close()`，`app.go` 没有注册 `WindowClosing` 拦截。已核对 beta.30：`Close` 触发关闭事件，默认监听销毁并移除窗口；`SystemTray.AttachWindow` 仅保存窗口引用，并不拦截关闭。结果是两种设置均走同一销毁路径。待在隔离 Windows 实例验证标题栏、Alt+F4、托盘菜单与后台任务，不将静态确认写成原生复现。

**F06 / P3 / 设置页面的跨模式恢复规则未同步。** `modes/modeSessions.ts` 的漫画恢复白名单仍是 `/comic/me`，当前路由已将它重定向到 `/comic/settings`；记住后者被静默忽略，返回漫画模式恢复为更早的列表页。小说设置页虽在白名单中，但 router 将设置滚动保存为 `routeScreenKey` 产生的 `/novel/settings:分组`，该键也被快照的路由校验拒绝。直接运行当前纯函数：保存漫画设置仍返回 `/comic/library`；保存小说设置子页 480px 后回读 0。证据：`dist/audit/full-project/mode-probe/result.json`；复现脚本 `.cache/audit-mode-sessions.mjs`。该结论针对跨文档／跨模式快照，不代表同文档内的 router 内存滚动恢复也失败。视频设置被现有测试明确列为不恢复页面，未将该设计直接报成缺陷。

复现 Go 用例在 `.cache/audit-startup_test.go`，通过 `.cache/full-project-overlay.json` 虚拟映射到 service 包，未向正常测试树加入故意失败的用例。命令：`go test -overlay .cache/full-project-overlay.json ./app/service -run '^TestAudit' -count=1 -v`；当前三个测试按预期失败并保留日志 `dist/audit/full-project/startup-probes.log`。这些是发现故障的证据，不是修复后的回归通过记录。

**F07 / P1 / Android 同进程 Activity 重建崩溃。** MuMu Android 15、当前源码构建的 2.4.1 验收包在 `am start --activity-clear-top` 后触发 `panic: application is running or a previous run has failed`，进程 SIGABRT；冷启动可恢复。`MainActivity.onCreate` 再次 `nativeInit`，但 Wails 应用单例仍运行。证据：`dist/audit/full-project/android-lifecycle/result.json`、`native.log`。该段为修复前复现；2.4.2 已修复并通过连续三次同进程重建，见当前状态表。

**F08 / P1 / Windows 改名导致浏览器数据不可见（已修复）。** Wails beta.30 在未设置 `WebviewUserDataPath` 时，将 `%APPDATA%/<exe 文件名>` 当作 WebView2 数据目录；原生重复试验里旧名可读 `cczj_ep_prog_v1`、旧数据弹窗状态和 IndexedDB，改名后这三项全为 null。本项目 SQLite 位于 `%APPDATA%/CCZJ Video`，改 EXE 名本身不会搬走该库。已在 `app/storagepaths` 固定浏览器资料身份，首次选择最近使用的既有正式版资料目录并记录于 `webview-profile.json`；后续始终读该目录，选中目录消失或记录损坏时明确失败，不偷偷建立空目录。旧目录不复制、不删除，避免对运行中的 Chromium 数据作不一致复制。`scripts/test-windows-storage.py` 在隔离资料下实测旧名写入、改名重现丢失、修复后以新旧名读回三种内容。仍需审查历史多个资料目录的用户数据如何合并；当前只接续一个已有目录，不会自动把不同目录的条目混写。`episodeProgress.ts` 同时修正 `writeStorage` 返回 false 时错误地清除待写标志。

Android 验收包使用相同 `applicationId` 和签名，以任意 APK 文件名 `adb install -r` 后，SQLite 文件 SHA-256 前后相等，WebView 测试键可读；证据 `dist/audit/full-project/apk-storage/result.json`。`build/android/build.ps1` 的 `ApplicationId` 可选 preview/acceptance，这两个包身份彼此隔离；只改 APK 文件名不影响 Android 应用身份。未覆盖“更换 applicationId／签名后卸载重装”的数据迁移，不能把它称为同一应用升级。

修复验证：`scripts/verify.ps1` 退出码 0，更新后前端 71 文件／333 测试通过；Windows production 标签构建成功，`scripts/test-windows-storage.py` 原生四次启动断言通过；修改后的文档链接检查通过。完整脚本日志在 `dist/audit/full-project/storage-fix-verify.log`，浏览器资料证据在 `dist/audit/full-project/windows-storage/run-bma2f5sq/result.json`。未对用户现有资料目录运行修复版，避免审查中写入用户数据；首次实际升级接续仍需观察现场结果。

### 已排除的旧结论与待跟进线索

- 旧 A-001／A-002／R13 的“静态无限线程池、MainActivity 不持有 JS 桥”不再适用于当前源码：现有线程池有 4 线程／64 排队上限，Activity 会先调用 `jsBridge.shutdown()`，回调有 closed 检查。本轮 F01 是该有界实现的取消路径问题。
- Go → Java 的另一条 `WailsBridge.executeJavaScript` 仍持有 WebView 并 post 回调，`shutdown` 未清空引用或清除 Handler 队列；JS 桥 closed 检查不能覆盖此路径。需要结合 JNI 销毁／Activity 重建继续验证，暂不计为已复现缺陷。
- `RestartApp` 的两次拉起若均失败，第二次错误被忽略，仍进入退出；需要可控进程启动失败实验，暂不计为已复现。
- `ServiceShutdown` 收尾超时提前返回，而 beta.30 从 shutdown 清单移除服务后不会重试；需检查宿主最终退出顺序及后台写入，不能仅凭“数据库保持打开”注释认定任务得到收尾机会。
- Android Activity 重建路径已原生复现为 F07，继续检查 onDestroy/初始化幂等与返回恢复。

## 执行方法

1. 保存工作区状态清单，识别其他开发者的未提交工作。按职责绘制模块和关键调用链索引；同时检查 Go 服务、Vue 调用方、原生桥与构建脚本。
2. 运行现有完整验证并保存基线。对未覆盖平台单列任务，不能因根目录 Go 测试通过而跳过 Android Java。
3. 从用户任务贯穿审查，而不是只按文件审查。至少覆盖首次使用、日常使用、异常中断、重试、退出、重启、升级与恢复。
4. 确定性故障先写能触发原问题的回归用例；资源/性能问题先量测，再修复。静态风险需说明触发条件，不推断发生频率。
5. 按数据丢失/安全与崩溃、核心任务不可用、错误状态与资源、体验细节排序。先处理共用底层问题，再做页面改造。
6. 允许有依据的重构，但同步迁移所有调用方、兼容数据及验证。已有视频体验优先保留；共享改动必须回归视频。
7. 每轮交付更新缺陷台账与覆盖矩阵，不以增加文档代替修复，不以删断言或调宽阈值制造全绿。

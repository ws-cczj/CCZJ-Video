## 完成的含义

完成不是改完用户点名的问题，而是建立模块清单、检查关键调用链、覆盖异常与平台差异、修复已确认的问题并给出证据。无法证明“所有可能的问题都已消失”；必须明示检查范围、遗漏和无法验证的环境。

不要将检查清单伪装成检查结果，不要将一次全绿测试写成全项目无缺陷。每项审查记录：模块、入口/调用链、检查方法、平台、结论、证据和后续动作。状态使用“未查 / 审查中 / 已查有问题 / 已查未发现问题 / 待平台验证”，所有模块必须有状态。

## 执行方法

1. 保存工作区状态清单，识别其他开发者的未提交工作。按职责绘制模块和关键调用链索引；同时检查 Go 服务、Vue 调用方、原生桥与构建脚本。
2. 运行现有完整验证并保存基线。对未覆盖平台单列任务，不能因根目录 Go 测试通过而跳过 Android Java。
3. 从用户任务贯穿审查，而不是只按文件审查。至少覆盖首次使用、日常使用、异常中断、重试、退出、重启、升级与恢复。
4. 确定性故障先写能触发原问题的回归用例；资源/性能问题先量测，再修复。静态风险需说明触发条件，不推断发生频率。
5. 按数据丢失/安全与崩溃、核心任务不可用、错误状态与资源、体验细节排序。先处理共用底层问题，再做页面改造。
6. 允许有依据的重构，但同步迁移所有调用方、兼容数据及验证。已有视频体验优先保留；共享改动必须回归视频。
7. 每轮交付更新缺陷台账与覆盖矩阵，不以增加文档代替修复，不以删断言或调宽阈值制造全绿。

缺陷记录格式：

```text
ID / 严重性 / 模块 / 平台：
状态：用户报告、已复现、代码确认风险、待验证、已修复、已回归
触发条件与最短操作：
预期与实际：
代码位置及调用链：
复现命令、日志或截图：
根因与修复：
回归结果、未验证环境、残余限制：
```

风险不等于已发生的缺陷；检查未发现问题不等于证明不存在问题。与此次行为无关的纯格式化、大范围重命名和依赖升级不得混入修复。

## 两端验证要求

浏览器替身用于隔离前端问题；Windows Wails 验证真实绑定、桌面生命周期及系统能力；Android 验证 Java/Go/JS 桥、WebView 和设备交互。三者结果分别列出。

移动验证包括系统返回、触摸取消、软键盘、横竖屏、安全区、权限拒绝、网络切换、切后台、Activity 重建、进程终止后恢复、亮度/音量/PiP 退出恢复。仅改变浏览器视口宽度不能称为移动端验收。

桌面验证包括键盘焦点、窗口缩放、最大化/全屏、关闭期间保存、重复启动、文件选择、更新与回滚。仅通过前端构建不能称为桌面验收。

数据恢复、升级及破坏性用例使用隔离目录、数据库和测试包，不清空用户真实数据。记录源码版本/工作区快照、构建产物、设备、WebView 版本和测试数据，防止测旧包交新源码。

## 文档清理原则

全仓文档也在范围内，按当前实现、可执行流程与真实证据核对。删除已失效且无独立价值的设计指导；保留有效外部格式、迁移契约和复现证据。报告可标记为历史，不让其“已完成”覆盖当前故障。

删除前保护未提交原文，记录删除理由并修复引用。不要因时间旧就清空 `docs`、`reports` 或所有技能；不要为了新方案删除有效安全、兼容和数据恢复约定。阅读相关已清理项见子任务文档。

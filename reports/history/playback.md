### 诊断页面与插件信任修复（2026-10-13）

<a id="origin-diagnostics-page-2026-10-13--页面改动"></a>

#### 页面改动

诊断中心仍从「设置 → 诊断」进入，但按一个完整页面布局：固定页头、刷新与报告导出，六个分区按需切换。资源概览保留原有内存卡片、趋势和进程明细；播放、网络与缓存、采集源、豆瓣补全、运行环境与存储不再堆成一条长页面。

独立诊断页由分区内容纵向滚动；嵌入设置时，由设置页的主内容区统一负责纵向滚动，避免高度不成立的嵌套滚动区域拦截滚轮。表格只在宽度不够时横向滚动。导航根据实际内容宽度转成横排，支持鼠标拖动、触控和点击；竖向滚轮不转换成横向操作。资源组件持续挂载，切换分区不会清掉趋势。采集源支持搜索、异常筛选和直接可见的错误原因。身份合并候选在第一次打开豆瓣分区时加载，后续手动刷新与合并成功继续更新；合并原有确认流程保留。

<a id="origin-diagnostics-page-2026-10-13--信任弹窗的原因与修复"></a>

#### 信任弹窗的原因与修复

用户本机的内置诊断清单是 1.0.0，没有后续新增的 `icon` 字段。旧实现拿磁盘内容与当前构建的嵌入内容摘要直接比较，合法旧版也不相等，因此启动会询问信任。此外，已授权脚本任一文件变化也会要求再次确认。

修复后：

- 原版内置包自动运行，包含缺少图标的早期清单，以及诊断 1.0.0 / 1.1.0。全部声明字段和执行文件仍需与已知原版相符，目录名不能单独建立信任。
- 原版旧诊断清单迁移到 1.2.0；修改过的脚本、声明和删除过的目录保持用户选择。
- 未获信任的新外部脚本在启动、重扫、拖放安装后保持禁用，不弹窗、不执行模块顶层代码。
- 仅在明确点击启用时确认一次，持久化后才启用与执行；正常更新和重启沿用已确认的插件授权。
- 拒绝保留至撤销，扩展包页提供清除信任并停用；卸载清掉记录，重装后按新插件处理。信任记录不参与用户备份迁移。

修复前的回归信号：`go test ./app/plugin -run TestBuiltinTrustRecognizesShippedLegacyManifestWithoutIcon -count=1` 失败，提示原版无图标 1.0.0 在启动时会弹信任窗口；前端授权测试发现更新后询问两次。修复后这些测试及原有内置包保护测试均通过。

<a id="origin-memory-optimization-2026-10-13--图片与后台界面的内存优化2026-10-13"></a>

### 图片与后台界面的内存优化（2026-10-13）

<a id="origin-memory-optimization-2026-10-13--范围与原因"></a>

#### 范围与原因

用户实际报告中主程序私有提交约 68 MB，Go 活跃堆约 4.2 MB；WebView 子进程约 355 MB，占总私有提交约 84%。本轮集中优化图片资源和后台界面工作。

实际复现了三个问题：

- 给 `<img>` 的 `loading="lazy"` 没有延迟前面的图片代理调用，120 张列表海报仍立即发起 120 次代理请求。
- KeepAlive 缓存页面只触发停用，不卸载。图片原图地址继续被节点持有；诊断依赖的设置标签 `active` 仍为 true，导航到其他页面后会继续轮询。
- 图片代理内存缓存只限制 80 条，没有字节预算。20 个较大的返回值仍全部被保留；失败 URL 的冷却记录也没有数量上限。

<a id="origin-memory-optimization-2026-10-13--改动"></a>

#### 改动

1. 代理请求随真实视口懒加载，在视口外预留 240px 以减少滚动时的等待。所有图片共用一个观察者，取消、停用和卸载都会收回注册。
2. 页面活动状态统一组合 KeepAlive、document.visibility 和 Wails 窗口隐藏/最小化事件。应用根组件维持窗口状态；所有组件共用一份文档监听及原生事件订阅，最后一个订阅者卸载时释放。
3. 隐藏图片从节点移除原图地址，返回时恢复图片。路由切换保留约 750ms 缓冲，使用一个共享释放计时器，快速返回可复用原图；窗口隐藏、最小化和卸载立即释放。恢复已显示的旧图跳过重复淡入，避免快速切页导致 GPU 分配反复增长。列表状态和设置草稿继续由 KeepAlive 保留。
4. 图片字符串缓存同时限制 80 条和 8 MB 的 UTF-16 保守估算预算，超限按 LRU 淘汰。单条超过预算仍能供当前图片显示，但不挤掉其他缓存或留在内存缓存中。失败 URL 冷却记录最多 256 条，并保留近期失败的冷却行为。
5. 诊断页停止隐藏路由的采样；恢复时继续更新并保留精简历史。网络与缓存分区及导出报告增加图片字符串估算与预算，明确排除解码像素和 GPU 内存。
6. 首页轮播在隐藏、最小化或缓存停用时停止。后台改变轮播设置也不会重新开启它；窗口和页面恢复后继续工作。

本轮没有调整视频画质、解码器或 HLS 缓冲预算。后台采集、下载、播放不由这套界面活动状态停止；浏览器回归验证隐藏窗口资源处理后，正在播放的媒体仍前进。

<a id="origin-memory-optimization-2026-10-13--受控对比"></a>

#### 受控对比

在 Windows 上用独立 Chrome、120 张各不相同的 480×720 图片、相同布局进行三轮前后对比。只替换 Wails 绑定，实际 Vue、RemoteImage、图片解码、KeepAlive 和浏览器进程运行。历史图片组件与缓存来自 Git 提交 `c900bb131d8d82d680d96816fb549dcfce4193a1`；不需要还原工作区。历史测试文件放在忽略的构建输出目录，生产构建会清理它们，构建脚本检查它们没有被嵌入应用。

通过 CDP 获取该隔离浏览器的进程 PID，Windows API 读取其私有提交；没有把其他浏览器进程合并进来。测试专用 GC 区分保留堆与待回收垃圾，生产应用不强制 GC。

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 首屏图片代理调用 | 120 | 24 |
| 持续隐藏后的原图地址节点 | 120 | 0 |
| 隐藏诊断路由期间新增采样 | 1 | 0 |
| 浏览器私有提交，第 1 轮 | 485.1 MB | 391.7 MB |
| 浏览器私有提交，第 2 轮 | 508.2 MB | 389.2 MB |
| 浏览器私有提交，第 3 轮 | 502.3 MB | 380.9 MB |
| 浏览器私有提交，中位数 | 502.3 MB | 389.2 MB |

中位数减少约 113.1 MB / 22.5%；首屏代理请求减少 80%。MB 按 1024² 换算。原始记录在 `dist/audit/optimization-legacy-final-*.json` 和 `optimization-after-final-*.json`，汇总为 `optimization-summary.json`。最早完整代码基线的隐藏轮询读数保存在 `optimization-before.json`；历史图片复放仅替换图片模块，诊断轮询已经修复，因此不能把历史图片复放中的轮询当成旧版诊断行为。

快速切页试验也发现，立即释放且重复淡入会造成原生 GPU 分配继续增长，因此补充释放缓冲和恢复跳过淡入后重新验证。最终三轮测试的第 12 到第 24 次切页，私有提交约为 558.2→558.1、547.5→546.6、541.7→541.0 MB，均趋于稳定；闲置后分别回落到 532.5、507.2、511.6 MB。JS 堆保留增量约 217～225 KB，DOM 节点 1,242→1,250，事件监听器 315→315。

这些数字来自固定浏览器场景，不是用户完整 Wails 应用的实测降幅。浏览器、GPU 缓存和驱动可在预热后保留分配，移除图片地址也不保证立即归还所有提交。真实海报尺寸、页面数量、主题和播放缓冲会改变结果；这次结果不能证明所有场景都不存在泄漏。

#### 问题一：完整缓存缺少关闭后的空闲预算

原有关闭路径停止媒体，但跨集 LRU 会一直保留在模块级 Map 中，只有更多片段进入并触及全局上限时才淘汰。它有 128 MiB 的全局上限，因此不能简单归为无界泄漏；但对关闭后长期空闲的程序，继续保留已观看多集的数十 MiB 数据没有必要。

通过真实 VideoPlayer 挂载、媒体加载、缓存写入和卸载路径复现：

```text
python scripts/test-player-idle-cache.py --channel chrome
{"playing_mib":70.0,"immediate_close_mib":70.0,"idle_mib":70.0}
AssertionError: player idle cache retained 70.0 MiB after closing
```

修复在 `utils/ts-cache/playback-lifetime.ts` 集中管理播放器持有期：每个挂载实例取得一个幂等释放句柄，最后一个实例退出时取消预取、清除会话索引，使迟到的工作失效。内存缓存保留 30 秒供快速重开，随后按 LRU 收缩为最多 **8 MiB、16 条**，磁盘缓存继续保留。新播放器打开会取消旧的回收计时，恢复播放期预算。空闲预算也约束后来写入的片段，避免详情页预热重新填满缓存。

磁盘回读增加会话 generation 校验。仅检查 episode key 无法识别“关闭 A 后很快重新打开 A”的旧读取；现在旧请求即使同 key 也不能回填新会话。

修复后同一浏览器命令得到：

```text
{"playing_mib":70.0,"immediate_close_mib":70.0,"reopened_mib":70.0,"idle_mib":8.0}
```

回归检查覆盖播放期间不收缩、快速重开取消旧计时、多播放器持有、迟到预取、关闭后重开同集的旧磁盘结果，以及空闲后新增片段仍受预算限制。诊断导出增加实际缓存预算、播放器持有数和待回收状态，关闭后也能看见回收进度。

```text
  → CSSTransition
  → KeyframeEffect
  → progress-buffer
  → 已脱离文档的 player-wrapper / video
```

这说明“页面上 video 数为 0”不足以判定旧节点已回收。先前的清理把子树 animation/transition 设置为 none，再调用 getAnimations；隐藏 WebView 在样式变化后可能已不再枚举旧动画，导致清理漏过仍被原生时间线持有的对象。

只改变动画清理顺序的三轮生产测试通过，最终节点 30、监听 52，未再逐轮累积。随后加入缓存回收的八轮生产测试也通过；测试中缓存因真实 HLS 加载从约 82 MiB 增至约 95 MiB，最后一轮关闭后收缩至约 6.69 MiB，最终节点 30、监听 52。进程树私有提交从关闭后的短测高位约 678 MiB 降至最终约 546 MiB；最终读数发生在测试主动 GC 后，不能承诺生产程序会以同样速度或同样幅度下降，也不能当作用户完整应用的新实测结果。

### 播放期内存优化：按需读取磁盘片段

本轮保留现有播放器、硬件解码、画质和 HLS 缓冲参数，优先减少代码控制范围内不必要的二进制读取。它不解决 WebView2 图形路径在关闭播放后的原生内存保留，相关边界见 [原生内存定位报告](playback.md#origin-webview-native-retention-2026-10-16)。

<a id="origin-playback-on-demand-cache-2026-10-17--已复现的问题"></a>

#### 已复现的问题

原实现会在 `setCurrentEpisode` 和 `setSegments` 中恢复整集磁盘缓存。后者也在 HLS 播放列表更新时调用，因此同一批片段可能重复进入 IndexedDB 的结构化克隆与内存缓存写入链路。`SegmentDiskCache.loadEpisode` 先批量读取该集所有二进制，再过滤过期项；最终 LRU 上限无法避免此前的批量读取峰值。

用真实 Chrome / IndexedDB、生产 `TsCache` 和 `TsCacheLoader`，向临时浏览器写入 40 个不同片段，每片 2 MiB，共 80 MiB。随后打开该集但不请求媒体片段。修改前，测试得到：

```text
opened_cache_mib: 80.0
binary_reads_on_open: 40
AssertionError: opening an episode restored unrequested segment binaries
```

该复现没有替换缓存或 loader 实现，浏览器配置与数据库均为隔离测试环境，不访问用户缓存。

<a id="origin-playback-on-demand-cache-2026-10-17--实现"></a>

#### 实现

- 切集、解析或刷新播放列表只更新索引，不批量恢复二进制。
- 播放 loader 先读内存；未命中时按同一归一化 URL / 字节区间键读取一个磁盘片段；仍未命中或 IndexedDB 不可用时联网。
- 磁盘先检查该键的 TTL 元数据，再读取二进制。过期片段不会先克隆进内存；数据长度异常也按未命中处理。
- 单次磁盘查询最多等待 250 毫秒，数据库阻塞时回退网络，迟到结果不回写，避免把可选缓存变成播放依赖。
- 后台预取同样按单片读取磁盘，避免取消整集恢复后反而重复下载已有片段。磁盘命中不计入网络速度样本。
- 异步结果沿用缓存会话代次、loader 请求代次和取消检查，切集或关闭后迟到的读取不会重新填入缓存。交给 HLS 的缓存副本与保留副本隔离，防止解码操作影响后续命中。
- 保留原数据库版本与数据，无需迁移。内存 LRU、磁盘容量、空闲回收策略和 HLS 前后缓冲预算保持原值。

<a id="origin-playback-on-demand-cache-2026-10-17--前后结果与限制"></a>

#### 前后结果与限制

| 同一磁盘缓存场景 | 修改前 | 修改后 |
|---|---:|---:|
| 打开该集时的内存片段缓存 | 80 MiB | 0 MiB |
| 打开时读取的磁盘二进制条数 | 40 | 0 |
| 请求一个 2 MiB 片段后的内存片段缓存 | 已批量恢复 | 2 MiB |

修改后的第二次请求使用内存命中，无额外磁盘读取或联网。后台预取另一个磁盘片段同样不联网；过期片段正确走网络且不读取过期二进制。测试同时覆盖读取中取消、迟到会话、磁盘不可用、字节区间与二进制副本保护。

这是**片段缓存与二进制读取量**的前后对比，不是整个软件内存从 80 MiB 降到 2 MiB。冷磁盘未缓存的内容不会因此明显减少持续播放占用；播放和预取实际用到的片段仍会进入有上限的内存 LRU。单片磁盘查询增加少量 I/O，不能仅凭本地测试承诺所有来源的首播时延不变。

### 实际播放过程的诊断记录

旧面板的实时趋势只在页面可见时采样，最多保留 150 点。切到播放器或最小化后停止轮询，是减少后台开销的正常行为，但不能据此判断一整段播放是否存在内存泄漏。

<a id="origin-playback-recording-2026-10-13--操作"></a>

#### 操作

1. 打开设置 → 诊断，点击「开始记录」。等按钮变成「结束并导出」后开始播放。
2. 正常播放 30–60 分钟，可包含切集、换线路、打开/关闭增强功能及最小化。出现问题时先保留现场，不必返回诊断页面。

<a id="origin-playback-recording-2026-10-13--捕捉范围"></a>

#### 捕捉范围

- Go 后台每 5 秒写一个资源快照：主进程和所属子进程的工作集、私有提交内存、CPU、进程数、句柄、Go 堆、GC、协程数和系统内存压力。使用单独的采样器，诊断页面的两秒采样不会扰乱其 CPU 时间区间。

- 开始和结束各保存一份 Go heap pprof 与协程栈。ZIP 包括时间线、前后剖析、最终诊断 JSON 和最终剖析文件。

#### 开销和退出

每次记录最多 6 小时、时间线约 32 MiB 或 10,000 个事件，达到限制会自动结束并保留数据；最后一个完整记录可能使文件略超大小阈值。正常退出应用会补存末尾样本、剖析和结束行。关闭到托盘不属于退出，记录仍继续。文件错误会终止任务并在面板显示错误。

<a id="origin-player-audit-2026-10-13--发现并修复的问题"></a>

#### 发现并修复的问题

| 问题 | 触发与影响 | 修复 |
| --- | --- | --- |
| 视频被整份当作播放列表读取 | MP4/WebM 等直接媒体地址也经过 `fetchAndParseM3u8`；原实现调用 `response.text()`，读完再交给 HLS 判定。大文件会产生额外下载、文本分配及缓存 | 检查 MIME 和首段 `#EXTM3U`；遇到非清单立即取消读取；真实清单按流读取，最多 8 MiB。自定义 HLS loader 也使用相同限制 |
| 清单缓存只限制条数 | 16 条大清单仍可占用大量字符串内存 | 同时限制 16 条和估算字符串总量 8 MiB；视频正文不进入清单缓存 |
| 清单加载未随换集取消 | 旧请求继续等待响应和读取正文，虽然后续界面回写已经受代次保护 | 传入播放会话的 AbortSignal，换集/关闭时取消真实请求 |
| 分片路径解析错误 | 相对代理 URL 会被拼成 `/__cczj//__cczj/hls…`；仅含查询参数的分片会丢失原清单文件名 | 以完整清单地址和页面 origin 按 URL 规则解析，不先截掉文件名 |
| 播放页面无限重试及迟到绑定 | 每次重试把次数重置为零；若从未找到播放器，会一直轮询。多处延迟调用不登记，离开后可能给另一页视频绑定监听 | 统一由 `mediaProgressTracker` 管理定时器和 AbortController；最多尝试 20 次；查找限定当前播放页面；卸载永久停止 |
| 页面异步挂载完成于卸载之后 | 源列表/历史读取较慢时，卸载先移除监听，旧挂载流程返回后又重新安装全局键盘、可见性和缓存订阅 | 各挂载 await 边界检查页面是否已经卸载；视频组件自身 nextTick 之后也检查 |

<a id="origin-player-resource-cleanup-2026-10-13--已复现并修复"></a>

#### 已复现并修复

<a id="origin-player-resource-cleanup-2026-10-13--隐藏缩略图视频的所有权和清理"></a>

##### 隐藏缩略图视频的所有权和清理

旧实现将清理函数和 URL watcher 挂在主视频上；异步 HLS 导入后再注册 watcher。主视频引用先消失时，无法调用这些清理函数，迟到的导入仍可能建立 HLS 实例。重复初始化也会留下旧隐藏视频。普通媒体路径移除 DOM 时没有暂停、清空 src、调用 load，因此没有明确重置解码资源。seek 超时只改标记，不移除事件监听。

四个失败测试在修复前分别复现：重复初始化出现三个隐藏视频、关闭后仍有存活 HLS、移除后的预览视频保留源地址、超时 seek 监听残留。

现在预览资源由一个独立所有者管理，不依赖主视频引用；URL watcher 同步注册在组件作用域中，仅有一份。关闭、切源、闲置均清理预览的 HLS、监听、定时器、src 和画布，迟到的异步初始化不能重新挂接。

正常观看不再创建第二个视频或 HLS 实例。首次悬停进度条时才建立预览，普通媒体只预加载 metadata；抓到一帧或离开进度条后停止预览 HLS 拉流，离开十秒后释放预览。主播放缓冲参数保持原值，没有通过减少正常播放缓冲来换取内存数字下降。

<a id="origin-player-resource-cleanup-2026-10-13--hls-加载器取消契约"></a>

##### HLS 加载器取消契约

缓存命中通过微任务返回。旧实现的 abort 只取消 fetch，未作废已经排队的缓存成功回调，也未向 hls.js 上报 onAbort。失败测试确认：取消后成功回调仍递交分片；随后确认缺少取消通知。

增加每次请求的代号，取消、销毁和重用实例会使旧异步结果失效；取消时正确通知 HLS，完成后解除回调引用。补齐 hls.js Loader 要求的 context 字段，销毁时清空请求上下文及控制器。复用加载器时只递交最新请求。

<a id="origin-player-resource-cleanup-2026-10-13--隐藏-webview-的动画时间线保留关闭节点"></a>

##### 隐藏 WebView 的动画时间线保留关闭节点

真实 WebView2 的 HLS 循环测试发现，关闭后节点数和监听数可能按每轮增长。一次八轮及五分钟静置的失败结果为：节点 488 → 3,788，监听 103 → 628。

前端堆快照找到以下强引用链：

```text
Document
  → DocumentTimeline
  → CSSAnimation / CSSTransition
  → thumb-halo / progress-played 节点
  → __vueParentComponent（开发构建中的元数据）
  → subTree
  → 已从页面移除的 native-video
```

只在关闭前调用 Animation.cancel 仍未通过测试：退出时将进度改回零，又触发了 CSS transition；隐藏 WebView 不及时推进动画时间线，关闭节点继续被保留。

现在关闭前先对播放器子树禁止 CSS animation 和 transition，再取消已存在的动画，然后执行媒体清理。禁用仅作用于本次正在销毁的播放器，重新打开会创建正常的新节点。修复后同一八轮测试通过，最后节点为 64、监听为 52，已挂接视频/画布为零。

开发构建中的 Vue 元数据放大了保留链的影响，因此也单独验证了生产版前端。不能把开发构建中这一链条的内存规模直接当成用户生产程序的损失量。

### 2026-10-16：进一步定位关闭后的数百 MiB 差值

主要增量已定位到本机 **WebView2 的 GPU 进程、ANGLE/D3D11 硬件图形路径中的 Windows 原生堆**。去掉播放器组件、HLS、TS 缓存及 Vue，仅保留一个原生 HTML 视频，也复现了约 271 MiB 的关闭后留存。因此，TS 缓存回收和播放器动画修复不能被描述为已解决这部分增量。

本轮没有找到同时保留原有硬件解码、GPU 合成能力，又能释放这部分原生堆的可靠改法；默认硬件渲染配置继续保留。低内存对照确实下降明显，但实际使用了软件解码，不能冒充没有代价的等价优化。本报告区分定位结论与尚未完成的底层释放方案。

<a id="origin-webview-native-retention-2026-10-16--修正测量方法"></a>

#### 修正测量方法

之前的回归测试基线在首次播放、关闭之后，已经包含一部分初始化成本；完全隐藏的 WebView 也不等价于用户可见窗口。本次增加首次播放前基线，使用屏幕外实际渲染的隔离原生窗口，测试专用开关只传给独立的 probe，不作用于用户程序。

第一组扩展原生测试，关闭后比首次播放前多 367.5 MiB。去掉缩略图和内存转储后，仍多 324.8 MiB；测试专用 GC 只减少约 11 MiB。基于此，进一步排除 Playwright 的 Network/Fetch 响应保留、Vite 开发客户端等测量开销：

- 新增 `scripts/profile-native-player.py`，只使用原始 CDP WebSocket；没有启用 Network/Fetch 域，没有浏览器路由拦截和响应体录制。
- 使用静态 HTTP 服务，生产 Vue/真实 VideoPlayer/HLS，只有 Wails API 接口模拟；媒体为本地生成的 1080×608、24 fps、H.264。
- 从首次播放前开始观察，主要读数不强制 GC。GC、内存压力通知、卸载页面作为末尾独立对照。
- 通过 `SystemInfo.getProcessInfo` 对齐真实 OS PID 与 GPU/renderer/browser 角色，而非按 exe 名猜测。
- 通过 memory-infra 原生内存转储查看分配类别。
- 所有测试都使用临时用户目录、独立进程，没有停止用户程序，没有打开用户数据库或修改显卡/系统设置。

<a id="origin-webview-native-retention-2026-10-16--核心复现"></a>

#### 核心复现

```powershell
python scripts/profile-native-player.py --tag raw-app --trace --controls --max-retained-mib 128
```

旧问题确实触发阈值失败：`Native retention 307.6 MiB exceeds 128.0 MiB`。128 MiB 是本次定位大额留存的测试阈值，不是操作系统对正常占用的标准。

本机组合：WebView2 **155.0.4283.45**（来自转储中的运行时路径），NVIDIA GeForce RTX 3050 Laptop GPU，驱动 **32.0.15.9282**；实际 GL renderer 是 NVIDIA ANGLE D3D11，媒体属性确认 `D3D11VideoDecoder`、平台解码为 true。实验没有启用软件内的画质增强。

| 阶段 | 进程树私有提交 | GPU 进程 | 页面 renderer |
| --- | ---: | ---: | ---: |
| 首次播放前 | 231.3 MiB | 83.1 MiB | 28.5 MiB |
| 播放中 | 586.5 MiB | 343.1 MiB | 111.2 MiB |
| 关闭并自然空闲 35 秒 | 538.8 MiB | 326.4 MiB | 78.4 MiB |
| 测试专用 GC 后 | 529.4 MiB | 326.4 MiB | 69.0 MiB |
| 再发临界内存压力通知 | 501.2 MiB | 292.5 MiB | 70.0 MiB |
| 卸载整个页面并 GC | 467.8 MiB | 292.3 MiB | 36.5 MiB |

自然空闲时约 307.6 MiB 增量中，GPU 进程贡献约 **243 MiB**，renderer 贡献约 **50 MiB**。缓存已收缩，GC 后也没有出现 GPU 大额回落。卸载整个应用文档后，GPU 仍比最初多约 **209 MiB**。

原生转储把其中约 **156 MiB** 的增长直接定位到 GPU 进程 `malloc/allocated_objects/win_heap`：约 6.4 → 162.1 MiB；相应 `malloc/win_heap` 提交约 7.4 → 169.0 MiB。已登记的 `gpu/shared_images` 关闭后约 13.6 MiB，不能用它代表全部显存或驱动分配。不同分配树节点存在父子和共享关系，不能相加作为总占用。剩余原生差值尚未细分到具体 DLL/函数；这里不把 GPU 进程原生堆的全部内存直接叫作显存，也不把“图形路径”擅自收窄为某个 NVIDIA 函数已经被证明泄漏。

<a id="origin-webview-native-retention-2026-10-16--最小化到原生视频"></a>

#### 最小化到原生视频

```powershell
python scripts/profile-native-player.py --tag raw-bare --bare --controls --max-retained-mib 128 --port 9282 --debug-port 9283
```

这个页面不加载播放器、HLS、TS 缓存和 Vue。关闭时明确 pause、移除 src、load 重置并删除 video。

| 阶段 | 进程树私有提交 | GPU 进程 |
| --- | ---: | ---: |
| 首次播放前 | 199.7 MiB | 73.6 MiB |
| 播放中 | 493.1 MiB | 335.4 MiB |
| 关闭后自然空闲 | 470.4 MiB | 313.4 MiB |
| 卸载页面并 GC 后 | 439.2 MiB | 289.9 MiB |

原生视频仍多出约 270.7 MiB，说明大头不依赖业务组件或 TS Map。结合实际转储，可将主要责任边界定位到这个运行时/硬件图形组合；它不等于证明用户完整应用的每一 MiB 都来自同一项。

进一步关闭 CDP Media 观察域，纯视频仍自然留存 **263.4 MiB**；GPU 为 73.7 → 307.7 MiB，卸载/GC 后仍为 290.3 MiB。这排除了 Media 观察域持有播放器这一测量假象。修正进程创建时间校验后的生产播放器再测仍留存 **301.3 MiB**，运行时确认是 `Edg/155.0.4283.45`。

#### 单变量对照

| 对照 | 关闭后相对首次播放前增量 | 实际能力/判断 |
| --- | ---: | --- |
| 默认硬件路径，原始 CDP | +307.6 MiB | D3D11 平台解码、GPU 合成 |
| 仅关闭硬件视频解码，扩展探针 | +297.4 MiB | 已确认 FFmpeg 软件解码；GPU 仍高，排除“单纯硬解缓冲”解释 |
| 关闭 GPU 合成，原始 CDP | +59.7 MiB | 实际变为 FFmpeg 软件解码，WebGL 为 readback；有代价 |
| 仅关闭 GPU 光栅化，原始 CDP | +305.6 MiB | 大额留存仍在 |
| 仅关闭 DComp 视频 overlay，原始 CDP | +298.2 MiB | 仍为 D3D11 平台解码，大额留存仍在 |
| D3D11on12 对照 | 约 +305 MiB | 仍高；该次发现采样器误计无关进程，不作为主要绝对数比较 |
| 请求 OpenGL 后端 | +60.7 MiB | 实际回退成软件图形及软件解码；不能当作硬件 OpenGL 修复成功 |

另做四次打开、播放、关闭，再自然空闲 60 秒：最终提交为 576.6 MiB，比首次播放前 216.6 MiB 高约 360.1 MiB；压力通知后降至 491.3 MiB，卸载/GC 后为 439.9 MiB。此短测不能证明长期无界泄漏，也不足以宣称已经进入完全稳定的平台。大块一次性图形初始化留存和后续较小的累积需要分开看。

上表不同探针的启动基线和测量开销不同，只用于归因，不能按几 MiB 的差异给渲染策略排名。原始 CDP 的默认、纯视频、关闭合成、关闭光栅化和关闭 overlay 是主要证据。

<a id="origin-webview-native-retention-2026-10-16--诊断采样器中的独立错误"></a>

#### 诊断采样器中的独立错误

在一次 D3D11on12 探针里，采样器把一个约 59 MiB 的 OneDrive 后台进程列为后代。原因是 Windows 的数字父 PID 会保留，父进程退出后 PID 可能被新程序复用。之前只按父 PID 递归，缺少创建时间校验。

已将进程树收集提取到 `app/resource/process_tree.go`。读取候选子进程的创建时间，早于当前父进程的记录会排除，并且不再沿其递归；读取失败则注明结果不完整。没有改成按进程名粗略排除，合法的辅助进程仍可计入。

回归先复现误计，再修复：`go test ./app/resource -run TestProcessTreeRejectsRecycledParentIDs -count=1`，覆盖根 PID 重用、子 PID 重用、相同时间戳、父进程已退出；采样句柄及 Windows 原生资源测试也通过。此错误可能放大某些报告，但不是这次默认/纯视频测试里约 200–300 MiB GPU 增量的来源。

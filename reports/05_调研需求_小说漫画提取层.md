## 1. 我们项目的现状（你的答案必须落在这里面）

技术栈：Wails v3（WebView2 / Android WebView）+ Vue 3 + Go 1.25 + SQLite（`modernc.org/sqlite`，纯 Go 无 CGO）。桌面 Windows 为主，Android 是预览包。**没有 Node 后端，没有浏览器扩展运行时，提取必须在 Go 侧完成。**

`go.mod` 现有直接依赖只有 5 个，**没有任何 HTML 解析库，也没有 `golang.org/x/net`**：

```
github.com/andybalholm/brotli v1.2.1
github.com/jmoiron/sqlx v1.4.0
github.com/wailsapp/wails/v3 v3.0.0-beta.30
golang.org/x/sys v0.46.0
modernc.org/sqlite v1.52.0
```

已经存在、新能力必须**延伸而不是另起**的机制：

- 源存在单表 `sources`，一列 `strategy_config` 装声明式 JSON（`app/model/source.go:51-73`）。
  已批准给这张表加一列 `kind`（video / novel / comic）。
- 现有声明式格式是 `StrategyConfig` v2（`app/collect/strategy.go:35-59`，
  schema 在 `docs/source-strategy-v2.schema.json`，`additionalProperties: false`）：
  每个操作一个 `ParamConfig`（只描述 **URL 查询参数叫什么名字**：
  `action` / `action_param` / `page_param` / `limit_param` / `type_param` / `keyword_param` /
  `hours_param` / `id_param` / `extra`），加一个 `ResponseShape`
  （只描述 **JSON 信封在哪**：`list_path` / `code_path` / `ok_codes` / `msg_path` /
  `page_path` / `pagecount_path` / `total_path`），加 `field_mapping`（标准字段名 → 源字段名）。
- 统一请求执行器 `collect.doFetchShape`（`app/collect/fetcher.go:233-297`）：
  30s 超时、32MB 上限、手动解 gzip/deflate/br、**非 JSON 预检**
  （`:268-276`，首字节不是 `{`/`[` 就报「源站返回了非 JSON 响应」）。
- 已经有完整 stale-while-revalidate + singleflight + 失败续命的进程内缓存
  （`app/detail/service.go:186-249`），和 sha256 键 + mtime-LRU + 原子写 + 失败冷却的
  磁盘图片缓存（`app/proxy/imagestore.go`）。这两套骨架直接复用。
- 同源 HTTP 代理路由 `/__cczj/hls`（`app.go:58-61` → `app/proxy/hls.go`）：
  流式转发、透传 Range、Content-Type 无限制、有 SSRF 防护
  （`safeDialContext` 在拨号瞬间复核）。但它把 Referer **截成 `scheme://host/`**
  （`hls.go:110-116`）且**不支持自定义 header**（`:213-221`）。
  我们会新开一条 `/__cczj/img` 路由补上「全量 Referer + 命名 header 集」。

两个已知的硬约束，你的答案如果与之冲突请直接指出：

- Go 侧出网**完全直连**：全仓非测试代码里 11 处 `&http.Transport{}` 字面量，
  只有一处显式写了 `Proxy: nil`（`app/cast/service.go:63`），其余根本没设这个字段
  → `Transport.Proxy == nil`，既不读 WinHTTP/系统代理也不读 `HTTP_PROXY`。
  （唯一的例外是 `netstats.WrapTransport(cat, nil)` 在 base 传 nil 时会回落到
  `http.DefaultTransport`，那一份带 `ProxyFromEnvironment`，用在源探测与更新检查上——
  所以「探测走代理、采集不走」这个不一致已经存在。）
- 已经撞过 **TLS 指纹墙**：`app/proxy/service.go:111-129` 记录了 `img9.doubanio.com`
  对本机 Go 客户端固定回 200 + 一段 JS 挑战页，curl 带同样的头却能拿到图。
  我们没有 uTLS，也没有任何指纹伪装库。

## 2. 我打算设计的接口（草案，用来对准你的答案）

下面是**我的**设计，不是任何开源项目的。请你按这个形状回答「哪些能力我必须加、
哪些可以不做」，而不是评论这个设计好不好看。

```
一个源 = 若干「操作」。每个操作 = 一次请求 + 一次提取。

操作集合（小说）：search / detail / toc / content
操作集合（漫画）：search / detail / toc / pages / image
  - toc     目录，可能多页（需要「下一页在哪」）
  - content 小说正文，可能章内多页（需要「下一页在哪」，且不能把下一章吞进来）
  - pages   漫画：章节页 → 图片地址列表
  - image   漫画：图片页 → 真实图片地址（两步解析的第二步，源能直接给地址时可省略）

每个操作可声明：
  请求侧：URL 参数名（沿用现有 ParamConfig）、method、body、
          **headers（键值对，含 Referer / User-Agent / Cookie）**、
          **encoding（auto | utf-8 | gbk | ...）**
  提取侧：format = json | html
          list   = 条目数组在哪（JSON 路径 或 CSS 选择器）
          fields = { 标准字段名: { 路径或选择器, attr?, 正则? } }
          next   = 下一页地址在哪（可空）
```

标准字段名我暂定这些，**请你按真实源的实际情况告诉我该增该减**：

- 通用：`id`（远端稳定标识）、`title`、`author`、`cover`、`summary`、`status`、
  `genres`、`updated_at`、`latest`
- 章节：`chapter_id`、`chapter_title`、`chapter_url`、`order`、`volume`、
  `access`（free / login / pay / unknown）、`uploaded_at`
- 小说正文：`text`（或 `paragraphs`）、`next_page_url`
- 漫画：`page_index`、`page_url`（解析页）、`image_url`（最终资源）、`referer`

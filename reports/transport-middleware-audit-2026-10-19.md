# 前后端交互与数据预处理统一审阅

2026-10-19，基于当前共享工作区源码与本地 Wails v3.0.0-beta.30 源码。此次完成架构审阅与实施清单，没有修改业务实现、运行设备测试或打包。其他会话的改动保留。

## 判断

适合统一的是每次交互都要遵循的执行流程：调用归属、取消、通用参数约束、返回值解码、错误、耗时观察和资源释放。具体字段语义由各业务提供解码器和校验器，公共流程负责调用它们。

数据处理还包括适合复用的有界解压/JSON 解码、设置保存队列等模块。这些模块可以被中间件调用，但不应把正文提取、分页续传、备份合并等全部塞进全局拦截器。

主要收益首先是统一管理、消除遗漏。性能收益需要来自可观察的工作减少，例如减少重复 IPC、响应转换、落后请求、写入次数和事件重绘；添加一层调用本身不会使业务计算自动变快。

## 交互入口与现有基础

| 入口 | 当前实现 | 结论 |
| --- | --- | --- |
| Wails RPC | 生成绑定目前导出 190 个方法；`frontend/src/api/app.ts:9` 集中转出 | 已有集中入口，但大部分只是透传，并未统一执行解码与观察。保留方法名、参数和成功返回格式。 |
| 后端公共错误 | `app.go` 显式安装 ServiceOptions.MarshalError，`app/apperror/error.go` 分类并编码 | 保留。复用公共错误出口，避免再发明一套成功/失败包裹协议。 |
| 后端调用流程 | `app/operation/middleware.go:26` 提供恢复、操作名、关联号、耗时和错误观察；服务层仅 `facade_danmaku.go` 使用 operation.Run | 优先扩展实际覆盖范围。现有错误出口兜底不等于每个操作都有名称、归属和耗时。 |
| 模式生命周期 | `app/service/requests.go:9` 关联请求与模式任务组；library、reading_state、部分 video 使用，弹幕另有保护 | 归属和取消需要按操作显式选择，避免业务入口重复遗漏。 |
| 前端可取消组合 | `frontend/src/api/requestChain.ts:9` 的 applicationRequest 跟踪每个在途绑定并统一失败类型 | 可作为前端公共调用流程基础；目前主要用于阅读组合请求与弹幕读取。 |
| 前端运行时校验 | `api/danmaku.ts` 有字段、整数范围、条数校验；`api/library.ts:61` 多数操作只判空，列表过滤空项 | 增加按业务声明的解码器，不能把生成类型或泛型当作运行时校验。 |
| 后端事件 | `api/events.ts:28` 统一订阅/解除，但类型标注和泛型重载不校验到达的数据 | 适合统一解码、归属过滤与有限进度合并。 |
| Android 桥 | `api/androidTransport.ts` 处理 JNI 包裹与取消回执，desktop 使用 Wails 原生通道 | 平台差异保留在传输适配；业务解码、错误与观察可以共用。 |
| 媒体 HTTP | `app/service/assets.go` 装配 HLS、阅读图片、Android 媒体端点 | 保留流式 HTTP 语义，独立于 RPC JSON 解码。 |
| 外部数据来源 | provider 管线、danmaku 平台适配器、netbudget/netpolicy、缓存和 workflight | 已有有职责的公共模块，继续复用，不再套一个重复的万能网络框架。 |

本地 Wails 的 `ServiceOptions` 提供 MarshalError 等装配项，没有通用的业务请求拦截器字段。实施可以扩展项目已有的类型化 operation.Run 与 API 适配器，不需要修改 Wails 源码、生成绑定或改成字符串方法名加任意参数的总入口。

## 优先收拢的六类行为

### 1. 调用归属、取消、恢复和观察

后端提供统一的类型化请求执行器，复用 operation.Run 和 lifecycle。每个入口声明操作名、所属范围（当前模式/宿主共享/后台任务控制）及确有必要的超时策略；领域处理函数继续显式接收 context。

前端统一组合调用与失败解码，保留 CancellablePromise。新增 async 包装如果丢失 cancel，统一就会使原本有效的取消失效。复用 applicationRequest 的取消所有权，视图或异步资源仍负责 generation，阻止不可取消的迟到结果回写。

需要避免的归属错误：

- 模式切换入口自身不能登记到它马上要 Stop 的旧模式组，否则可能等待自己结束。
- 用户主动下载的启动/暂停命令与长期下载任务是两个生命周期，关闭设置页不应取消已经确认的任务；切换模式仍按当前产品规则暂停并要求手动恢复。
- 更新、窗口操作和日志等宿主功能不能硬编码成视频模式。
- 写操作完成提交后如何反馈由业务决定，不能统一在“返回前检查取消”时把已经落库的成功伪装成未提交。

实际发现：`GetDoubanComments`（facade_douban.go:156）没有 context 参数；前端 DoubanComments.vue:55 虽持有可取消绑定，后端评论链路仍经无调用 context 的 fetch/等待路径。应同时改入口、等待和实际 HTTP，只有界面停止接收结果不能说明后端工作已停止。此项是源码结论，本轮没有运行时复现。

### 2. 入参规约与返回 DTO 解码

公共模块提供有限的解码/校验工具，业务声明字段、必填、范围、最大条数以及兼容规则。输入先校验再调用，输出在信任入口解码一次后交给界面。

具体接入点：

- video 的 VideoListReq / VideoSearchReq 已有自定义 JSON 解码；library 使用直接类型参数；reading_state 使用 JSON 字符串；danmaku 有自己的范围校验。可以共用数字/字符串 ID、边界检查等工具，但来源 ID 必须保持原值语义，不能一律转 Number 或全局 Trim 所有字符串。
- 搜索关键词、可选枚举、分页大小应有明确默认和上限；视频页码和阅读来源的不透明 cursor 仍由各自契约解释，不能强行改成同一分页协议。
- 阅读的 unwrapList 目前会过滤 null；批量书架解析则刻意保留 null 槽。公共解码器必须显式声明“过滤/保留/报错”，不能悄悄改变身份位置关系。
- `api/library.ts` 的返回值多数只判空；`stores/detailCache.ts:122` 通过类型断言读取缓存。适合在各自入口增加必要字段与形状校验，缓存坏了按缓存失效处理，远端失败按 API 失败处理。

不需要将每个已验证对象在每次渲染、每个 computed 中再完整扫描；网络、磁盘/WebView 缓存和原生桥分别是需要验证的信任入口。

### 3. 有界文件/JSON/压缩数据处理

公共载荷模块负责：输入字节上限 → Base64 或文件读取 → 识别约定压缩格式 → 解压后字节上限 → 单个完整 JSON 文档解码 → 交给业务结构校验。每条链路声明自己的预算，不使用一个全局超大上限。

实际发现：

- `facade_source_import.go:28/92` 文件与 Base64 两个入口重复识别 Brotli/gzip、解码 JSON。两条链路仅使用 LimitReader 加一次 decoder.Decode，没有统一证明解压后总长与 JSON 尾随数据符合要求。
- `facade_video.go:51` 的 DecompressDetailJSONBrotli 使用无界 io.ReadAll。
- `app/backup/service.go` 已有“max+1 读取后显式比较长度”的模式，可以提炼机制，保留备份与源文件不同的容量及格式契约。

统一后仍由各业务拥有来源文档校验、用户信任授权、备份合并事务和错误语义；全局解码工具不决定写入什么数据。

### 4. 设置加载与有序保存

统一设置模块支持键对应的解码器、缺省/兼容策略、同键写入顺序、进行中的编辑合并、可见失败以及重试未保存状态。后端对有副作用的键先校验、成功持久化再生效；读取兼容和保存严格度分别声明。

可复用 reading/persistence.ts 已有的“同身份只保留最新修改、批次成功后才移除待保存项”思路，但不把书架的业务记录协议推广到所有设置。

实际发现：`stores/theme.ts:1030` 在同步 try/catch 内调用 SetSetting，没有 await/catch 接住异步拒绝。统一保存器应使这类失败可见，避免当前界面已改但重启恢复旧值。该问题不需要扩展为整个主题系统重写。

已有 `SetSetting` 对模式切换、网络策略和弹幕源作特殊处理。可整理成明确的设置规则模块，但保留成功落库后才生效的不变量和旧键兼容，不机械替换成无约束的动态插件注册。

### 5. 事件载荷、来源身份与 UI 更新

在 api/events 层为已知事件配置运行时解码、模式/操作身份过滤与解除订阅；进度事件可以只保留一次绘制周期的最新状态，降低重复渲染。完成、失败、删除和切换事件应及时交付，不能被通用节流丢弃。

来源业务已经有 source_key、operation_id 等字段；对发起后仍会继续的任务，应按任务身份过滤旧事件，不能仅按“当前页面是否存在”判断。

未知/扩展事件仍由调用方明确提供解码器与权限语义，不把 TypeScript 泛型重载解释为数据已通过校验。

### 6. 统一诊断口径

调用流程记录固定操作名、当前模式、分段耗时、成功/失败/取消及公开错误码；错误沿用现有关联号。按需观察请求等待、业务执行和前端解码，不能将 IPC 往返、后端处理和源站 HTTP 耗时直接相加或混成同一指标。

成功高频请求以有限数字聚合，失败按现有策略记日志。WriteLog、诊断上报等入口应避免再次触发同一套前端报错上报，防止自我递归。不开启全参数日志，不记录 Cookie、源配置、正文或 SQL。

目前前端 activityDiagnostics 只允许 16 个不同操作名；直接给 190 个方法逐个打点会静默丢弃后续名字。应设计固定的有限分组/注册集合，按模式过滤，而非简单增大阈值。已有 network_policy 和 netstats 分别表示准入结果与真实流量，继续分开。

## 建议执行顺序

| 顺序 | 范围 | 验收依据 |
| --- | --- | --- |
| 第一批 | 复用 operation.Run / applicationRequest，补齐评论、阅读与详情的请求归属；修复设置异步保存失败 | 切换/取消后对应在途工作收敛；无旧结果回写；保存失败不冒充成功；错误含正确操作信息且不重复上报。 |
| 第二批 | 有界载荷解码与业务 DTO 解码；复用到源导入、详情缓存、备份和设置 | 超限/坏格式/尾随内容明确失败；现有合法数据、来源身份、null 位置、返回格式兼容。 |
| 第三批 | 事件解码与进度合并；完善模式诊断与热点 IPC 合并 | 任务完成事件不丢；同一操作 IPC/写入/重绘减少；固定观测项覆盖已接入操作；非当前模式无活动请求。 |

逐批迁移实际调用方，沿用类型化绑定；需要给 Go 入口补 context 时重新生成绑定并验证 Android/desktop 传输兼容。错误恢复、数据校验、事务、请求复用、缓存和重试分别保持所有者，避免形成一个依赖全部业务的全局中间件包。

## 性能判断与边界

评估相同业务操作的 IPC 次数、载荷字节数、并发/取消计数、解码耗时、后端处理时间、重复落库次数与内存变化，再判断哪部分工作实际减少。当前报告是源码审阅，没有采样数据，不宣称毫秒、内存或百分比提升。

原有正常请求频率和普通失败重试仍保持；五分钟以上随机冷却继续只用于新增弹幕相同请求。事务、删除、导入、播放控制等写操作不统一自动重试或合并；可复用读取也必须明确来源和身份，流式媒体继续使用独立通道。

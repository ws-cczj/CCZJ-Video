# 弹幕源接口结构核对与可行性判断

日期：2026-10-19。状态：设计评估，未修改业务代码、数据库、绑定、来源设置或安装包。

## 结论

可以做独立的弹幕源管理，与采集源管理并列。已有普通弹幕适配和 Canvas 播放链路能够继续使用，扩展应集中在 Go 的协议适配、来源身份、匹配与缓存管理。

但不能承诺“任意 URL 导入即兼容”，也不能把“当前窗口没有弹幕”当成“这个库没有该视频”。支持范围必须由已经核对的协议和能力决定。当前条件足以设计并实现受控的来源接入，不足以让任意外部库仅凭片名无提示地自动替换。

本次判断来自当前源码、用户交接文档及 ZIP 内固定源码快照；没有访问新的弹幕服务部署，没有重新运行 UI、测试或打包。历史联网读取记录只作为已有链路的证据，不代表所有第三方部署现在可用。

## 已核对的三层接口

### 1. 平台原始接口

| 来源 | 定位与请求链 | 内容结构 | 归一化关键点 |
| --- | --- | --- | --- |
| B站 | 名称搜索 → 投稿分P/番剧单集 → `cid`，辅以 `aid` → `/x/v2/dm/web/view` → `/x/v2/dm/web/seg.so` | 元数据和分段为 Protobuf | `progress` 已是整段视频绝对毫秒；分段号从 1 开始；不能用 BV/aid 代替 cid，也不能再次添加分段偏移 |
| 腾讯 | 搜索 → 作品 cid → 具体单集 VID → `/barrage/base/{vid}` → `/barrage/segment/{vid}/{segment_name}` | JSON；`segment_index`、`segment_span` 和 `barrage_list` | `time_offset` 已是绝对毫秒；按返回索引定位；`total=0` 不足以判空；`content_style` 是需再次解析的 JSON 字符串 |
| 爱奇艺 | 搜索/详情 → 具体 TVid → baseinfo 时长 → 60 秒分段 `.br` | 文件本身 Brotli 压缩，解压后为观察到的 Protobuf，另有 XML 兼容分支 | `showTime` 为绝对秒，乘 1000；页号从 1 开始；不能再加页偏移；目录与签名由适配器处理 |

实现证据：`app/danmaku/bilibili.go`、`qq.go`、`iqiyi.go`、`decode.go`。原始文档：用户提供的 B站、腾讯和爱奇艺开发交接 Markdown；固定样本在 `app/danmaku/testdata`。此前三家实际读取及缓存复用结果见 `reports/danmaku-errors-2026-10-19.md`，本轮没有把历史结果当作新的测试结果。

### 2. 交接包中的聚合接口

在 `腾讯视频与爱奇艺弹幕接口_交接包.zip` 内只读检查了：

- `reference/danmu_api-source.zip`，固定快照 `5ef63a01bae7c4bad4dcd7bafbbcdcf33aa82564`。
- 重点读取 `worker.js`、`apis/dandan-api.js`、`models/dandan-model.js`、`utils/danmu-util.js`、`utils/cache-util.js`、`sources/tencent.js`；未执行其中代码。
- `reference/danmaku_go-source.zip` 的 README 另有通用、DPlayer、ArtPlayer 等输出入口；仅看到这些入口不能认定响应结构相同，本报告不将它们都列为已可直接接入。

`danmu_api` 快照存在完整的只读链路：

| 操作 | 已有路由 | 映射到本项目 |
| --- | --- | --- |
| 搜索 | `GET /api/v2/search/anime?keyword=...` | `Provider.Search`，映射作品候选 |
| 选集 | `GET /api/v2/bangumi/{animeId}` | `Provider.Episodes`，读取 `bangumi.episodes` 等明确结构 |
| 弹幕/分段描述 | `GET /api/v2/comment/{commentId}?format=json`，可带 `segmentflag=true` | 普通 `comments` 响应或 `segmentList` 分支，必须按结构区分 |
| 按视频定位 | `GET /api/v2/comment?url=...&format=json` | 已确认远端页面的读取定位方式；不等于按名称自动确定正确作品 |
| 读取分段 | `POST /api/v2/segmentcomment?format=json` | 将该接口给出的分段描述提交回同一个已配置服务，转换为 `Provider.Segment` |

已观察的普通 JSON 输出为包含 `count/comments` 的对象。单条 `p` 为 `时间秒,模式,颜色,来源标签`，`m` 为文本；此快照还输出自增 `cid`。分段描述含 `type/segment_start/segment_end/url`，可附带其他适配字段，不能按普通弹幕条目解析。

必须处理的实际差异：

1. `utils/danmu-util.js:423–432` 的 `cid` 是每次转换生成的序号，不能充当跨段稳定弹幕 ID。应使用真实上游 ID；没有时在同一个来源和单集内用时间、文本、模式、颜色形成近似指纹，并记录这一降级。
2. 同文件将毫秒转换为秒后保留两位小数；接入端再转为整数毫秒，已经损失的上游精度不能恢复。四字段 `p` 也不能按 B站 XML 的八字段 `p` 解释颜色位置。
3. `apis/dandan-api.js:2228–2262` 对部分非本地目录按数组下标生成或重新编号集数。`episodeNumber=1` 不一定能独立证明它是正片第一集，不能据此直接自动绑定。
4. `cache-util.js` 维护作品与单集引用分配、缓存和裁剪；单集引用还关联 `link.url`。不能未经部署验证就假定数字 commentId 永久稳定，应同时保存经确认的稳定定位信息，失效后重新解析并校验身份。
5. 聚合服务可能已经合并、筛选或偏移时间轴。归一化输出以该服务实际返回时间为基准，本地校准只追加一次；不能声称仍保留所有原始平台细节，也不能把未知的服务端偏移再补一次。
6. 返回的分片 URL 和临时字段留在后端适配器内部。CCZJ 不因响应里出现一个 URL 就直接抓取它，不把临时凭证写入播放器数据或普通日志。

因此，这一固定协议具备接入条件；具体用户部署仍需核对基础路径、协议版本、鉴权、两种内容分支和实际响应，不能仅凭接口名称宣称兼容所有“弹弹兼容”服务。

### 3. CCZJ 内部接口

现有 `Provider` 已有四个有实际差异的操作：`Search / Episodes / Index / Segment`。三家适配器负责签名、元数据和解码，`Service.ReadWindow` 负责缓存、时间窗口和去重，播放器只消费普通条目。

当前统一条目：

```json
{"id":"远端标识或空字符串","timeMs":1000,"text":"纯文本","mode":1,"color":16777215,"fontSize":25}
```

约定继续保留：字符串 ID；整集绝对整数毫秒；模式 1 滚动、4 底部、5 顶部；24 位 RGB，黑色 0 有效；高级脚本弹幕不执行。窗口封装已有 `provider/episodeId/startMs/endMs/cached/stale/warnings/skipped`。这些字段足以绘制普通弹幕，但不足以完整表达新来源身份与自动匹配依据。

## 底层怎样归一化

建议保留现有协议接口，增加真实来源实例与解析能力；不把每个外部响应格式分支放进 Vue。

```text
弹幕源管理：来源实例、协议类型、启停、默认项、补位顺序
                     ↓
后端来源选择与绑定解析：已确认身份、能力、失败原因、取消
                     ↓
协议适配器：平台原始接口 / danmu_api 固定协议 / 其他经验证协议
                     ↓
统一作品/单集信息 → 统一分段索引 → 统一普通条目
                     ↓
来源隔离的 SQLite 缓存 → 播放窗口 → 同一 Canvas 渲染器
```

需要补齐的模型与职责：

- **来源实例与协议类型分开。** 本地生成稳定 `sourceId`；协议选择 `adapterKind`；地址、鉴权引用和影响读取的配置有版本。两个同协议的不同库也是两个来源。来源显示名称和优先级变化不应无故清空内容缓存。
- **来源与内容平台分开。** 一个聚合库可能同时提供腾讯、B站等内容；它的服务地址身份不能用 `provider=qq` 代替。前端窗口及迟到结果校验也必须携带来源身份和读取版本。
- **平台专有参数留在适配器。** B站 aid、签名、分片 URL、聚合服务请求描述不是所有来源的通用字段；持久化时以有版本的适配器定位数据保存，对播放器只给必要的展示和状态。
- **作品信息保留未知值。** 标题、年份、季号、真实集序、正片/预告/特别篇、语言与版本、时长分别表达。现有 B站候选 `Year` 放的是 `pubtime` 文本，`Number` 也是平台显示文本；必须按协议转换，不能只改字段名便把它当作可靠年份和数字集序。不存在的元数据不补成“第一季/正片”。
- **能力按接口事实声明。** 可搜索、可列目录、可读分片、只能整集读取、只能按 URL 手动绑定分别处理。缺少搜索能力的源可以手动使用，不能参与按名称自动探测。
- **整集接口单独限制。** 没有分片接口时可把受限的整集响应视作一个内容对象，一次获取并缓存后供本地窗口读取；不能在每次拖动时重新全量下载。超过响应、条数或预算限制时明确不支持该资源，不无限制吞下。
- **归一化时校验。** 按协议固定时间单位、字段位置和枚举；校验有限数字、文本长度、条数和解压大小；解析失败保留错误。去重仅在当前来源、单集和内容版本内进行，默认不混合多个库。

来源配置建议独立保存为 `danmaku_sources`，不要塞进当前会被视频采集调度读取的 `sources`。弹幕绑定记录可包含多个已确认的备选，但当前播放只选一个；切源时替换窗口并清除旧轨道，避免同片段重复。

缓存标识至少包含 `sourceId + 内容配置版本 + 适配器/解码版本 + 稳定单集定位 + 分段标识`。延续内容缓存至少 1 天新鲜期、抓取后最多 30 天淘汰和现有总容量约束；无结果探测与短期健康状态另设较短期限，不能把超时或临时引用失效缓存为 30 天“没有该片”。修改读取配置后旧内容仍按原版本隔离，不能偷用。

用户导入的是来源配置，不执行配置里的任意脚本。既有平台客户端的固定域名校验继续保留；自定义协议使用按来源配置隔离的客户端，校验目标、重定向和请求头，凭证不跨来源发送。若以后支持用户自建局域网库，需要单独显式的端点授权与网络策略，不能简单删除现有 SSRF 检查或放开所有内网地址。

## 默认源与补位如何成立

顺序建议：当前单集用户固定来源 → 默认来源 → 用户启用且允许补位的来源。关闭弹幕后不继续探测，小说和漫画模式不启动这条链。

| 观察到的状态 | 是否足以触发自动替换 |
| --- | --- |
| 默认库明确找不到作品或对应正片单集 | 可以继续查备用源；找到候选后仍需校验身份 |
| 已确认同一作品、同一集、同一版本的备用绑定 | 可以自动补位，不覆盖用户固定项；展示来源变化及原因 |
| 只有相似片名、下标集号或缺季/版本的信息 | 仅列候选，首次要求用户选择；不使用“相似度超过阈值”冒充身份确认 |
| 当前时间窗口弹幕为空，或某一个分片 404 | 继续正常播放/记录缺段，不推出整集无弹幕，不自动轮换库 |
| 超时、401/403、429、结构变化 | 保留各自错误；429 遵守退避。若用户允许故障补位，仅切换到已经确认的备用绑定，不能把故障记成“未收录” |
| 用户取消、切集、切模式 | 取消当前整条查找及读取链，不再启动下一来源 |

绑定的时间偏移归属于具体来源和单集。换到另一库不能自动套用上一库偏移，也不能按总时长比例强行拉伸时间轴。

探测由一个后端流程拥有，按优先级进行，复用现有网络预算（弹幕最多 2 个并发），为整次探测限定总时长、来源数和请求数。不能让每个来源各自跑完整 45 秒后再轮到下一个，不能每次 seek 都搜索所有库。当前会话固定已选结果，明确失败或用户换源才重新解析。

管理页面与采集源页面并列；移动端放设置的管理入口，不增加底部导航项。播放器内保留开关、样式、当前来源、候选确认和快捷换源。用户控制导入、默认和补位范围；软件仍需负责输入校验、正确归一化及可靠的资源管理。

## 实施前必须通过的判断点

1. **具体协议闭环。** 搜索 → 正确目录 → 单集 → 分片或受限全量内容，每一步保存可复现且脱敏的响应；验证空结果、业务错误和数据结构变化的区别。只有内容下载接口的源按手动能力接入。
2. **身份与迁移。** 两个不同库即使返回相同数字 ID 也不串缓存；兼容现有三家已确认绑定，不删数据重建。新来源、绑定和偏好的备份/恢复要一起考虑，鉴权与信任不随普通内容备份自动转移。
3. **匹配可靠性。** 同名不同季、预告穿插、下标生成集序、特别篇、缺时长都不误绑；来源补位只自动消费可核对的绑定。
4. **运行预算。** 快速切集、拖动、关闭弹幕和模式切换后停止在途及后续探测；响应、条数、缓存和并发均有上限，整集接口不重复下载。
5. **可解释诊断。** 仅视频模式记录来源 ID、协议版本、选中原因、失败分类、请求耗时/取消、缓存命中与回退；不记录令牌、完整敏感 URL、临时鉴权字段或整份弹幕正文。

在这些条件下值得实施；某个协议缺少必要信息时，应缩小它的能力或拒绝接入，不能通过猜字段、吞错误和宽松匹配让功能表面可用。

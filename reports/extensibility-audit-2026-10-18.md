# 扩展性与性能架构复查（2026-10-18）

后续实施：四项 P1 已在交接后的第一阶段修复，见 [实施与验证记录](upgrade-phase1-2026-10-18.md)。本文保留修复前的调查证据；随后完成下载可靠性、阅读持久化、核心网络预算、共享读取、分页与工具链升级，见 [收尾实施记录](upgrade-phase3-2026-10-18.md)。本文保留调查时的证据，不代表所有表格问题仍未处理。

本报告是调查结论，不新增开发约束。统一规范仍为根目录 `AGENTS.md`。检查的是当前工作区，包含其他协作者正在完善的小说/漫画代码；不把整个脏工作区的改动归因于本轮。

## 结论

还有架构问题，其中一些已经影响功能正确性，不能只归为“以后规模大了再优化”。当前适合继续演进成模块化单体：稳定的基础设施、明确的领域能力、可替换的来源与平台适配器。没有证据支持现在拆微服务、替换 Wails、给每个结构体生成接口，或者把所有业务都改成插件。

“像框架一样可扩展”应落实为：增加一种实现时改动集中，任务和资源有所有者，协议能表达实际来源能力，策略能配置并受到资源预算约束，旧数据与调用方有迁移路径。它不意味着新增一种业务领域永远不用修改数据库和核心代码。

## 证据与边界

- 静态追踪：来源创建、阅读搜索/分页/正文、图片代理、缓存淘汰、模式装配、视频来源策略、数据库与应用初始化。
- 隔离执行探针：`extensibility-audit-2026-10-18/probe.go.txt`；结果：`extensibility-audit-2026-10-18/probe-results.json`。探针在独立 Go 进程中使用临时目录与本地 HTTP 服务；私网访问开关仅对该探针进程生效，没有打开用户数据库或修改持久配置。
- 探针源码以 `.txt` 保存，避免变成项目构建包。复跑时复制到临时目录的 `main.go`，在仓库工作目录执行 `go run <临时 main.go>`。
- 本轮没有修改产品实现，没有重跑全套验证。上一轮通过的验证结果不能替代本轮新增问题的回归测试。本轮也没有做生产数据规模的延迟、内存或吞吐基准。
- 优先级：P1 为已存在的正确性/协议缺口；P2 为扩展瓶颈或资源管理风险。表中的 P2 不等于已经证明线上卡顿。

## 发现

| 优先级 | 问题 | 证据与影响 | 改造方向 |
| --- | --- | --- | --- |
| P1 | 来源身份由域名片段推导，会冲突 | `model.DeriveSourceKey`；探针三个不同地址都得到 `example`；阅读 `AddSource` 遇到相同键直接冲突 | 来源持久身份与地址、名称、模式分离；为新增源分配稳定身份，保留已有键的兼容映射 |
| P1 | 图片缓存身份遗漏请求上下文 | 同 URL、不同来源头应返回不同 PNG，第二次却命中第一次图片，上游总共只访问一次 | 缓存与失败冷却使用一致的完整请求身份，包含来源、配置/认证上下文版本及影响表示的 Referer/头信息 |
| P1 | 正文缓存丢失完整性信息 | `ChapterText` 写入时只保留段落，命中时没有 Warnings | 缓存带版本的内容结果，保留完整性状态；明确截断内容是否缓存及如何重新获取 |
| P1 | 来源分页游标在编排层断掉 | `searchOne` 调用 `pipeline.Search(..., page, "")`；上层没有接收各源游标的入口 | 按来源保存、传递和校验分页状态，而不是只传一个全局页号 |
| P2 | 请求取消与并发预算没有贯穿调用链 | API 保留 cancel，但领域/页面 async 包装变成普通 Promise；搜索 semaphore 每次调用新建 | 显式传递取消信号；应用预算、来源/主机预算与操作局部并发分层；相同在途资源合并 |
| P2 | 阅读列表与来源统计不适合大数据量 | 列表 SELECT 全部记录、完整 DTO 返回；来源列表逐源 COUNT | 数据库分页/筛选/投影，批量统计；目录和视图也需按规模选择分页或虚拟化 |
| P2 | 依赖实例化仍有大量进程全局状态 | DB instance、detail.Default、globalScheduler、全局事件发布器与 updater hook | 应用装配根拥有实例；业务模块接收所需依赖，兼容全局入口逐步退场 |
| P2 | 缓存生命周期与请求路径仍耦合 | 图片冷读 8 个请求产生 8 次上游访问；写缓存偶尔同步全目录淘汰；规则编译缓存没有回收 | 按等价身份合并在途请求；后台/增量淘汰；编译规则按来源版本拥有或设置有界缓存 |
| P2 | 模式和来源扩展协议尚不完整 | 模式注册表之外仍重复枚举模式；视频策略主要表达 URL；仍有“接口冻结”的注释 | 集中模式描述与能力声明；来源请求与响应能力分离，保留旧策略适配器 |

### 1. 来源身份不是“域名的简称”

位置：`app/model/source.go:36`、`app/library/sources.go:88`。

探针输入：`https://api.example.com/novel`、`https://api.example.com/comic`、`https://example.cn/api`，三个键均为 `example`。共用 sources 表时，这会阻止同站多模式、多接口乃至不同域名的合法来源并存。

应区分持久 source ID、来源类型、内容模式、显示名称和可变化的入口 URL。不要为了修正命名立即批量重命名旧键：收藏、历史、书架与缓存已经引用它们。先为新增来源提供不冲突的身份，再设计旧身份迁移与导入导出的兼容策略。

### 2. 缓存必须保存“同一个请求”的结果

位置：`app/proxy/imgproxy.go:128`—`157`。

请求实际携带 sourceKey、完整 Referer 和来源头，但读取、冷却与写入都只使用 `upstream.String()`。探针用同一地址按不同来源头返回两张不同的图片，第二个来源实际收到第一张图片，状态仍为 200。失败冷却键相同，也会让一个上下文的失败暂时影响另一个。

应先定义请求身份，再共同用于成功缓存、失败缓存与在途合并；配置或认证上下文改变时同步失效。敏感头不能直接写进文件名或日志，应使用摘要/不透明上下文版本。若使用 Cookie 会话，也需要明确会话的来源归属和变化后的缓存策略。单纯把 sourceKey 拼在 URL 后面，仍不能覆盖同一来源更新请求头的情况。

### 3. 内容状态不能在缓存后“变正常”

位置：`app/library/content.go:197`、`:228`、`:250`。

首次抓取根据 `Truncated/Garbled/FontObfuscated` 生成提示，但缓存 entry 只有 Paragraphs。二次命中直接构造没有 Warnings 的 ChapterText。静态路径可确认提示必然丢失；本轮没有为该问题单独执行端到端探针。

缓存结果应包含可恢复的状态字段和格式版本，而不是只存展示文本。对于截断结果，要区分“允许展示部分内容”和“整章已经完整缓存”；调整限额后也应有重新获取路径。保持抓取限额，但让限额与内容完整性成为明确的契约。

### 4. 支持游标不能只停在底层字段上

位置：`app/provider/pipeline.go:53`、`app/library/service.go:369`、`app/service/facade_library.go:78`、`frontend/src/novel/data/novelLibrary.ts:34`、`frontend/src/comic/data/repository.ts:53`。

Pipeline.Search 已接收 nextURL，SourceResult 也返回 nextUrl；编排层却固定传空字符串，绑定入口只接受 kind/keyword/page，前端转换结果时又没有保留游标。只提供下一页链接/不透明游标的来源无法正确继续搜索，通常会重复第一页。按页号构造 URL 的来源不受同样影响。

需要一份带请求身份和来源键的搜索会话/分页状态：每个来源分别记录游标、完成、失败与重试状态。一个源结束后不应因另一个源还有下一页就不断重查。当前增量搜索事件也只有 SourceResult，没有请求 ID；将来接入页面渐进显示前，应增加请求关联与事件类型定义，避免并行搜索结果串入。

### 5. 防止旧结果回写与停止旧工作是两件事

位置：`frontend/src/reading/asyncResource.ts:56`、`frontend/src/novel/data/novelLibrary.ts:34`、`frontend/src/novel/views/NovelSearch.vue:16`、`frontend/src/comic/views/ComicCatalog.vue:24`；后端 `app/library/service.go:336`。

generation 能防止旧响应污染视图，这部分是有效设计。底层 Wails Promise 的 cancel 也已保留，但 `async/await` 领域函数及页面回调返回的是新普通 Promise，资源层无法继续调用其 cancel。旧工作仍可能出网、解析和入库。

搜索的 6 路上限是每次调用的上限，并非注释声称的全局上限。多次搜索可叠加；每次还会为所有源创建 goroutine，只有实际执行受 semaphore 限制。建议建立有限队列及共享预算，并保持章节抓取、播放、下载、后台采集的优先级差异，避免所有模块共用一个容易互相饿死的队列。

### 6. 数据增长后，不能把数据库当成完整数组接口

位置：`app/db/library.go:451`、`:472`；`app/library/service.go:245`；`app/library/sources.go:40`；`app/library/service.go:201`。

阅读作品列表没有 LIMIT，跨源读取完整记录，后续还要生成 DTO、序列化并传给 WebView。来源列表是一条列表查询加逐来源 COUNT。图片代理在需要来源头时查库并重新解析完整来源文档，也没有共享的版本化配置快照。

这些是明确的工作量增长路径，不是已完成的性能测量。建议分页与筛选下推数据库、列表字段投影、统计批量查询、来源文档按版本编译复用。作品转 DTO 已用 names map 避免同一列表中对同一个来源重复查名，应保留，不能误报成逐作品 N+1。

### 7. 有 Service 类型不等于依赖已经隔离

位置：`app/db/sqlite.go:25`、`app/detail/service.go:66`、`app/handler/scheduler.go:43`、`app/cache/invalidate.go:50`、`app/service/app.go:190`。

当前仍依赖单个默认 DB、默认详情缓存、全局调度器，以及最后一次设置生效的事件发布器和退出 hook。对单窗口单资料库能工作，但独立测试、多资料库、多运行实例或服务嵌入时，状态所有权不清楚。上一轮加入 db.Open 并没有自动让所有调用方改为使用实例连接。

应以 App 装配根管理 Database、缓存、调度器、事件出口和关闭顺序，再按模块迁移消费侧依赖。无需给每张表创建通用 Repository，也不要用一个巨大“框架上下文”替代所有全局变量。

### 8. 共享资源应合并重复工作，并能回收

位置：`app/proxy/imagestore.go:140`、`:176`；`app/provider/extract.go:339`、`:566`。

探针中 8 个并发冷读全部成功，但上游被访问 8 次；没有同身份在途合并。实现合并时，应允许某个等待者独立取消，不能让第一个等待者退出就取消其他仍需要的请求。

磁盘缓存淘汰有时间间隔，**不是每次写入都扫描目录**；但触发时在写入调用路径中同步遍历目录，超额后排序。规则的正则/CSS 编译已有缓存，**不是每次正文都重复编译**；问题是进程级 sync.Map 不回收，连无效规则错误也保留。来源反复编辑、导入删除后，这些对象的生命周期与来源脱离。

优先用来源版本持有编译结果，或采用容量有界的共享缓存；磁盘淘汰是否改索引/后台任务，应由文件数量与延迟测量决定，不能仅凭代码形状宣称已经变慢。

### 9. 扩展点应表达能力，不应冻结历史限制

位置：`frontend/src/modes/definitions.ts`、`frontend/src/App.vue:33`、`app/model/source.go`、`app/collect/strategy.go:13`。

APPLICATION_MODES 是好的起点，但 normalize、routeMode 和 modeShells 仍各自列出三种模式。新增模式需要同步多个事实源。应从描述表推导可推导的匹配、壳与导航，数据库持久枚举的迁移仍需显式处理。

视频 SourceStrategy 的方法主要返回 URL，适合现有 CMS；未来 POST、请求体、鉴权、游标和不同响应协议无法靠“再拼一个查询参数”完整表达。可逐步引入请求描述与执行/解码能力，给现有策略提供兼容适配。阅读 JSON/HTML 已有真实的 backend 实现切换，可保留；不要强行把视频、小说、漫画所有操作塞进一个巨型接口。

该文件仍有 `stays frozen` 注释。稳定兼容接口有价值，但这句话不能禁止有迁移方案的演进。另外，“超过 16MB 基本不是图片”“正文不会自己变”等注释把经验当成事实。应写成可配置的资源政策、默认值依据和测试边界。不能因此直接删除尺寸/分页/超时防护。

## 建议落地顺序及验收

1. **先修数据与协议正确性**：来源身份、缓存上下文、正文完整性、按来源分页。验收覆盖同站多接口/多模式、同 URL 不同上下文、配置变更、截断内容二次读取、仅游标分页和源间不同步翻页；旧收藏/历史/书架仍能解析。
2. **再补资源控制**：打通页面到 I/O 的取消，共享预算与在途合并，按版本持有来源配置。验收包括快速连续搜索只保留必要工作、取消一个等待者不影响另一个、冷读去重、应用关闭可等待任务释放。
3. **随后按规模优化数据路径**：分页投影、批量统计、规则缓存回收和磁盘淘汰。以 10/100/1000 来源以及不同作品数、缓存文件数测量查询数、RPC 大小、峰值内存、P95 延迟和队列等待，保留可复跑的基线。
4. **最后收敛装配与扩展协议**：依赖实例化、模式描述、来源请求能力。用增加一个测试模式/另一种请求协议验证改动集中程度；维持旧绑定和配置兼容适配，不通过大规模目录改名冒充架构升级。

可保留的基础包括：共享出网判据、JSON/HTML 提取适配、结构化错误出口、请求与关闭关联、资源 generation 防迟到回写，以及视频与阅读各自的领域结果。后续重构应围绕上述缺口深化这些模块，而不是推翻所有已有边界。

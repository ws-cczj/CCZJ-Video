## 1. 最重要的一个结论：我不需要规则字符串切分器

Legado 有一个 14KB 的 `RuleAnalyzer.kt`，是手写的、引号与括号感知的字符串切分器。
它存在的**唯一原因**是 Legado 把多种语法压扁进了一个字符串：分隔符 `&&` / `||` / `%%` /
`@` / `##` 都可能合法地出现在 CSS 属性选择器、JSONPath 过滤表达式（JSONPath 原生支持
`&&`/`||`）或正则里，所以切分时必须跳过平衡括号与引号。它还要处理两套不同的转义策略
（选择器语境里引号内反斜杠无特殊义，JS/JSON 语境里有），括号不平衡直接抛错。
【核实：`analyzeRule/RuleAnalyzer.kt:91-159, 165-298`】

**我们的格式用结构化字段**（组合与回退用数组/对象表达，选择器是一个独立的字符串值），
所以这套复杂度**整块不需要**。序列化层（JSON）替我们解决转义。

这一条直接决定了实现量级：省掉一个词法分析器、省掉一套转义规则、省掉「规则写错在
哪一层报错」这个长期调试面。需要保留的只有一个事实：**选择器字符串内部可以含引号、
括号、甚至 `@`**，所以不能对它做任何字符串切分。

## 2. 能力清单

### 2.1 纯声明式即可表达的主干（我们要做的）

按数据流顺序：

```
请求描述（method / headers / body / retry / 参数编码字符集）
  → 响应解码（编码探测三级）
  → 列表选择（一种选择器方言 + 索引/区间）
  → 字段终端（text / 属性名）
  → 组合（拼接 / 回退 / 交错）
  → 正则替换
  → URL 绝对化
  → 分页追链（next*Url）
  → 变量存取
```

各项的确切语义（以 Legado 实现为参照，**语义采纳、语法不采纳**）：

| 能力 | 语义（采纳） | Legado 里的写法（仅作识别，不照抄） | 证据 |
|---|---|---|---|
| 拼接 | 依次执行各子规则，结果**全部追加合并** | `&&` | 【核实】`AnalyzeByJSoup.kt:118-122,188-192`；`AnalyzeByXPath.kt:82-86`；`AnalyzeByJSonPath.kt:114-118` |
| 回退 | 按序执行，**第一个返回非空结果的胜出并停止**，后续不执行。不是"默认值"，也不是并集 | `\|\|` | 【核实】`AnalyzeByJSoup.kt:104-107,146-148,174-177`；`AnalyzeByJSonPath.kt:60-64,99-104` |
| **交错** | **按下标 zip**：`[A0,B0,C0, A1,B1,C1, ...]`，短列表越界跳过，迭代次数以第一个子结果长度为上界 | `%%` | 【核实】`AnalyzeByJSoup.kt:110-117,180-187`；`AnalyzeByJSonPath.kt:107-114,154-161` |

| 预处理 | 先用一条规则把响应体**替换成某个子元素**，后续所有规则相对它求值 | `ruleBookInfo.init` | 【核实】`BookInfo.kt:58-64` |

**交错（`%%`）值得单独说一句**：它对应的是「标题和链接分别在两个平行列表里」的站点
（例如 `<div class="titles">` 与 `<div class="links">` 分开排版）。这类站点真实存在，
所以我的格式要能表达"两个字段各自取列表，然后按下标 zip 成条目"。这是结构化格式里
很容易漏掉的一种组合形态。

## 3. 字符编码：确切的三级探测链

【核实：`help/http/OkHttpUtils.kt:79-95`、`utils/EncodingDetect.kt:18-58`】

Legado 的响应解码顺序：

1. 显式传入的 `encode` 参数——**书源管线从不传**（全库唯一调用点无参）
2. HTTP `Content-Type` 头里的 charset
3. `EncodingDetect.getHtmlEncode(bytes)`：截取 `<head>…</head>`，解析 `<meta charset>`，
   再解析 `<meta http-equiv=content-type content=…charset=…>`
4. icu4j `CharsetDetector` **统计探测**（`EncodingDetect.kt:55-58`）
5. 兜底 UTF-8；解码前先剥 UTF-8 BOM

**一个反直觉的事实**：URL option 里的 `charset` 字段**完全不参与响应解码**，
它只影响**请求参数**的百分号编码字符集（`AnalyzeUrl.kt:242,287-298`）。
所以 GBK 站能不能读对，靠的是上面那套自动探测，不是源配置。

**对我们的影响（Go 侧）**：需要
- `golang.org/x/net/html` 或 goquery（解析 `<meta>`）
- `golang.org/x/text/encoding/{simplifiedchinese,traditionalchinese,japanese}` 做转换
- 一个**统计探测**方案。Go 生态没有 icu4j 等价物，这是 `05` 任务 D 仍然要查的点。
  退一步的方案是：header → meta → **在源配置里允许显式声明 encoding**（我们有这个字段，
  Legado 反而没把它接到解码上）→ 兜底 UTF-8。显式声明这一级 Legado 缺，我们补上，
  因为我们的源是用户自己加的，加源界面上给一个编码下拉是自然的。

## 4. 分页与失败识别：确切参数

### 4.1 Legado 的循环**没有数值上限**

【核实：`BookContent.kt:83-110`、`BookChapterList.kt:65-86`；
grep `maxPage|MAX_PAGE|maxChapter|contentLimit` 在 `model/webBook/` 下**零命中**】

正文分页与目录分页的 while 循环终止条件只有三个：下一页 URL 为空、URL 已在去重集合里、
命中下一章 URL。**没有最大页数，也没有最大正文字节数。**

去重是 `ArrayList.contains` 上的**原始字符串精确匹配**（非规范化 URL），线性查找。
【核实：`BookContent.kt:57,85,90`；`BookChapterList.kt:49,69-70,193-201`】

→ **我们不照抄这一条**。`reports/00:98` 明确要求「新引擎需同时设置最大页数与最大正文大小，
防止错误规则无限跟页」。我们要加数值上限（默认值见 §5），并用**规范化后的 URL 集合**去重。

### 4.2 防「把下一章吞进本章正文」

【核实：`BookContent.kt:50-55,64,86-89`】三层：

1. 已知的下一章 URL：优先用调用方传入的，为空则查数据库 `index+1` 章的 url，再回退第 0 章 url
2. 循环内把 `nextUrl` 与 `mNextChapterUrl` 都用 `NetworkUtils.getAbsoluteURL(redirectUrl, …)`
   绝对化后做**字符串相等**比较，相等即 break
3. 把下一章 URL 通过 `setNextChapterUrl` 暴露给规则层，让源规则自己排除

**它的弱点**【推断，基于代码只做绝对化】：只绝对化，不归一 query/fragment。
下一章 URL 带了不同的签名参数就拦不住。→ 我们的实现要在比较前**剥掉 fragment、
并对已知的易变 query 参数做归一**，或者至少同时比较 path。

### 4.3 并发与顺序

【核实：`BookContent.kt:83-136`、`BookChapterList.kt:65-115`、`utils/FlowExtensions.kt:110-127`】

按「单页解析出的下一页 URL 个数」分流：

| 情况 | 方式 | 并发度 | 顺序 |
|---|---|---|---|
| 每页 1 个 next URL（链式分页） | 串行 while | 1 | 天然有序 |
| 一页解析出 >1 个（页底列出全部页码） | 并发 | `AppConfig.threadCount`，**默认 16**（`help/config/AppConfig.kt:234-235`） | `channelFlow` 按发射序 `send(async{})`，下游按序 `await()`，`.buffer(0)` → **完成乱序但输出严格按输入序** |

并发分支传 `getNextPageUrl=false`，即一次性列表，不再递归跟随。

→ **这个模式值得采纳**：并发抓取 + 有序合并 + 并发分支不再递归。16 太高，
我们的默认值另定（§5）。

**两个我们不复制的缺陷**：

1. 「没有 content 规则就把章节 URL 当正文返回，且下游无区分」——`reports/00:100` 专门点了这一条，

   不依赖字符串非空判定成功」。我们的 `Content` 是判别联合，`kind` 必填。
2. 「图片不校验内容类型就写缓存并标 Ready」——`reports/00:146` 要求「检查响应类型/解码，
   不缓存错误页为图片」。我们在**写缓存前**校验 Content-Type 与魔数，不合格不进缓存、
   直接判错。我们视频侧的采集器已经有一条同源经验的预检
   （`app/collect/fetcher.go:268-276`，首字节不是 `{`/`[` 就报「源站返回了非 JSON 响应」）。

**「200 但是登录页」没有先例可抄**，这一条得我们自己定判据。可用的信号：
Content-Type 与阶段期望不符、魔数不符、正文长度低于阈值、命中可配置的关键字/选择器。
我们至少要做到**能报出来**，而不是把登录页当正文缓存下来。

|---|---|---|
| Ready → Queue | imageUrl 已被缓存逐出 | `:71-73` |
| Error → Queue | 订阅该页自动重试 / 手动 `retryPage` | `:76-78,96-99` |
| Queue → LoadPage | imageUrl 为空，开始两步解析第一步 | `:227-229` |
| LoadPage → DownloadImage | 需下载（force 或不在缓存） | `:233-235` |
| DownloadImage → Ready | 图片写入缓存，stream 指向缓存文件 | `:246-248` |
| 任意 → Error(e) | 任何非取消 Throwable | `:257` |
| **任意 → Queue** | **CancellationException**（翻页取消 chunk 链，防止卡死） | `:251-256` |

→ **直接采纳这 5 个状态与「取消回 Queue 而不是回 Error」**。取消是可重试的，不是失败。
这一条和我们已经拍板的前端五态（loading/error/empty/取消/generation）能对齐：
后端页状态机是资源级的，前端五态是视图级的，两层不混。

## 5. 章节稳定标识与目录刷新

### 5.1 Mihon 的匹配键**只有 URL**

【核实：`SyncChaptersWithSource.kt:67-68,76-77,105-109`】

1. 远端列表先 `distinctBy { it.url }`
2. 本地建索引 `dbChaptersByUrl = dbChapters.associateBy { it.url }`
3. **唯一匹配键 = 章节 URL 精确字符串相等**。没有"再按标题、再按序号"的第二级匹配

URL 存的是 `setUrlWithoutDomain` 处理过的**去域名相对路径**（path + query + fragment，
`HttpSource.kt:428-463`）。所以**换域名不影响匹配，但 query 里的签名参数会**。

**兜底只有一条**【核实：`:171-221`】：URL 匹配不上的旧章进 removed，其 `chapterNumber` 收进
`deletedChapterNumbers` / `deletedReadChapterNumbers` / `deletedBookmarkedChapterNumbers`
（TreeSet<Double>）；新章若 `isRecognizedNumber && chapterNumber ∈ deletedChapterNumbers`，
则**继承**旧章的 read / bookmark / dateFetch。

`chapterNumber` 由标题识别得出（`ChapterRecognition.parseChapterNumbers`），
**识别失败 = -1.0**；`isRecognizedNumber get() = chapterNumber >= 0f`
（`domain/.../chapter/model/Chapter.kt:22-23`）。所有基于 number 的兜底都有这个守卫，
所以多个 -1.0 的章节之间不会互相误配。代码注释原文：
「Recognize chapter numbers, from the whole list since names alone don't always tell」（`:100`）、
「numbers every similar name shares aren't the chapter number」（`ChapterRecognition.kt:112-115`）。

**没有** URL 相似度或规范化兜底。→ 远端 URL 加了签名参数，且章号识别失败，**已读状态就丢了**。

### 5.2 远端删章：Mihon 是**硬删除**

【核实：`SyncChaptersWithSource.kt:149-154,223-227`；`data/.../ChapterRepositoryImpl.kt:37-45`】
`removedChapters = dbChapters.filterNot { it.url in sourceUrls }` → 先取消其排队下载 →
`removeChaptersWithIds(removedIds)` 在同一事务内**物理删除**。

→ **不采纳**。`reports/00:109` 要求「目录删除可标记不可用，不应立即删除用户下载」。
我们用软删（`lifecycle_state`），本项目视频侧的 `source_videos` 表已经有这个先例
（`app/db/sqlite.go:277`，`UNIQUE(source_key, source_vod_id)` + `lifecycle_state` active/deleted）。

### 5.3 `sourceOrder` 假设远端「新→旧」且**不自动检测**

【核实：`SyncChaptersWithSource.kt:67-74,195-196`】`sourceOrder = mapIndexed` 的下标。
代码注释原文：「Sources MUST return the chapters from most to less recent, which is common.」
消费端：`ChapterSort` 按 sourceOrder **升序**（`domain/.../ChapterSort.kt:16`），
下载器 `sortedByDescending`（先下最旧，`Downloader.kt:367`）。

**倒序源会让语义反转**，代码里没有任何方向检测。【推断其影响：列表顺序颠倒、
`dateFetch` 分配逻辑（新章按 `nowInstant + itemCount--.milliseconds`）错乱、
`maxSeenUploadDate` 单调性假设失效（`:83-85,112-117`）】

→ 我们的格式里有显式的「列表反转」能力（§2.1），**由源配置声明方向**，不靠猜。
`order` 字段我们自己算，不复用远端下标语义。

### 5.4 Legado 侧的章节键

| 层 | 键 | 证据 |
|---|---|---|
| 解析期去重 | `LinkedHashSet<BookChapter>`，data class **全字段 equals**（url/title/isVolume/baseUrl/bookUrl/index/isVip/isPay/resourceUrl/tag/wordCount/…），去重发生在 index 重排**之前** | 【核实】`BookChapterList.kt:123-125`；`data/entities/BookChapter.kt:42-60` |
| 存储期 | Room 主键 = **(url, bookUrl)** 复合；唯一索引 **(bookUrl, index)** | 【核实】`BookChapter.kt:30-35` |
| 缓存文件名 | `%05d-%s.nb` = index + **标题 MD5**（不是 URL） | 【核实】`BookChapter.kt:162-167` |
| URL 缺失兜底 | 卷章节用 `title + index` 当 url；普通章用 baseUrl | 【核实】`BookChapterList.kt:230-244` |

**全字段 equals 做去重是脆的**——任何一个字段有差异（比如 tag 里带了抓取时间）就去重失败。
→ 我们的去重键只用 `remote_id`（= 规范化后的远端章节标识），不用整行。

**缓存文件名用标题 MD5 而非 URL** 这一点值得注意：它对 URL 变化免疫，但标题改名就会
产生孤儿缓存文件。我们的正文缓存键按 `reports/00:104` 用
`provider + provider_version + item_remote_id + chapter_remote_id`，两边都不依赖。

## 6. 新发现的未知：字体码位混淆

【核实：`analyzeRule/QueryTTF.java`（37KB，手写 TTF/OpenType 二进制解析器，
解析 `name/head/cmap/loca/maxp/glyf` 六张表，`:949-991`）；
`help/JsExtensions.kt:802-910`】

**手法**：站点下发一份码位↔字形被打乱的 WebFont。正文文本里的码点是错的，
但浏览器用该字体渲染时字形正确，**肉眼看不出异常**；直接抽 DOM 文本得到的是错字。

**Legado 的解法**：建立「轮廓数据（glyf 原始字节串）→ unicode」的映射，
用**错误字体**查该码点的轮廓，再用**正确字体**按轮廓反查真实 unicode，逐字符替换
（`java.replaceFont(text, errorFont, correctFont, filter)`，按 code point 而非 char 遍历，
`:874`）。轮廓字节相等即认为是同一个字——**以字形指纹做码位还原**。
字体以 SHA-256 为 key 做 LRU(4) 缓存（`help/CacheManager.kt:11,26-31`）。

**关键事实**：它**不在提取管线里自动触发**，唯一入口是 JS 宿主函数，
调用时机由书源作者写在 JS 规则里（全库 grep 无其他调用方）。

**不支持它的客户端会看到什么**【推断，基于上述机制】：
抓到的文本是**码点有效但字义错误的 CJK 字符**——不是方块/tofu（码点在 Unicode 里存在），
也不是编码乱码（与 GBK/UTF-8 无关），而是「看似正常汉字但内容被打乱」，
且同一码位在全站映射一致地错。从浏览器复制粘贴会得到同样的错字。

→ **这一轮不实现解密**（它需要字体文件解析，量级不小，且只被 JS 规则触达，
属于长尾）。但**必须能识别并报出来**，否则用户看到的是一屏"正常汉字组成的乱码"，
完全无法自查。识别信号【推断】：源声明了 `@font-face` 且正文里出现私用区码位
（U+E000–U+F8FF）或高频异常码位分布。至少要在源诊断里给一条
「这个源可能用了字体混淆，本项目不支持」。
